# Background

Things that explain the shape of this repository but are not needed to run it.
Read this when something looks arbitrary and you want to know whether it is.

## It is a port of an n8n workflow

The membership draft flow ran in n8n as `CBT - Membership Fee Email Drafts`
before it ran here. That workflow is kept as the fallback if this service has to
be switched off, and it is the source of the fidelity fixture below.

It is **not in this repository**: its Code nodes have the club's bank details,
the treasurer's name and the spreadsheet id hard-coded, and this repository is
public. The export lives wherever the club keeps its documents.

It is inactive, and should stay inactive. Two systems drafting the same emails
would double every guest's welcome.

### Why the tests are worth trusting

`tests/fixtures/reference_cases.json` is generated by running the **actual n8n
Code node bodies** out of the exported workflow JSON, across 29 rows. The fee
module is asserted field by field against it, and the email body character for
character. "Faithful port" is therefore a checked property rather than a claim,
and it is why `domain/fee.py` and `domain/email_template.py` are not to be
tidied: the shapes in them reproduce a published fee schedule that guests have
already received.

Regenerating it needs both the workflow export and the generator script, which
live with it outside this repository — the generator reads the workflow's Code
node bodies, so it is useless without them.

**Re-apply the club-details normalisation afterwards.** The n8n workflow has the
real IBAN, BIC, bank, account owner and signature hard-coded, so a freshly
generated fixture reintroduces all five into a public repository. They are
replaced with the placeholders from `domain/models.ClubDetails`:

| in n8n | in the fixture |
|---|---|
| the real IBAN | `DE00 0000 0000 0000 0000 00` |
| the real BIC | `XXXXDEXXXXX` |
| the real bank | `EXAMPLE BANK` |
| the account owner | `Club Treasurer` |
| the VP Membership's name | `The VP Membership` |

The fidelity property survives the substitution: what is being asserted is the
wording, the layout and the fee arithmetic, none of which these five values
affect. `test_no_real_club_details_are_committed_in_the_fixture` fails if the
normalisation is forgotten.

## The package is `clubops`, but everything in it is membership

The package is named for the repository's scope, not for the one flow it
currently holds. It was `membership` first; both it and the deployed services
were renamed before anything was committed or applied, while renaming was still
free. Afterwards it would have meant rewriting a public history and minting new
service URLs.

It is deliberately **flat**: `pipeline.py`, `jobs.py` and `web.py` sit directly
under `clubops/`. When a second area of work arrives, the open question is
whether they move down into `clubops/membership/` beside a sibling package. That
nesting is not built in advance, because its right shape depends on what the
second flow turns out to share.

The deployed names, for reference:

| | |
|---|---|
| `cbt-clubops` | the private service |
| `cbt-clubops-slack` | the public relay |
| `cbt-clubops-run`, `cbt-clubops-slack-run` | runtime identities |
| `cbt-clubops-scheduler` | Cloud Scheduler's identity |

What kept its old name is anything describing a **flow** rather than the system:
the scheduler job `cbt-membership-drafts` and the Slack channel
`#cbt-clubops-admin`'s predecessor. A Sergeant at Arms flow will sit beside them
under its own name, and `cbt-membership-drafts` will still be accurate.

## Why there are two Cloud Run services

Cloud Run's authentication setting is per *service*, not per route. Slack's
servers cannot present a Google ID token, so the endpoint Slack calls has to be
public — and making the existing service public would have exposed
`/jobs/membership-drafts` along with it.

So the public relay holds only Slack's signing secret and bot token, and reaches
the private service over HTTP with a minted ID token. A compromise of the
internet-facing half yields a Slack signing secret, not the club's mailbox.
`tests/unit/test_boundaries.py` enforces it: `slack_web.py` may not import the
credential-bearing modules, and `load_relay_settings()` may not read the private
service's variables.

## Why the application form's field placement lives in this repo

PandaDoc has no coordinate-placement API, and its "create template from file
upload" endpoint supports neither form fields nor field tags — so a stored
template cannot carry the placement. `scripts/build_form_fields.py` writes
PandaDoc **field tags** into the PDF as white text; that annotated PDF is the
template, is checked in, and is uploaded on every call.

The details of that — why tags must be white rather than invisible, why the ids
read `mtn`/`gf`/`f1`, and the six uploads it took to establish the rules — are in
[`FORM.md`](FORM.md).
